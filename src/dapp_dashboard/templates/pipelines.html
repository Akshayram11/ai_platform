Pipelines

Move data between systems with DataOS Nilus, in plain words: say where the data is, where it should go and how it changes. The right pipeline (a one-time copy, a scheduled sync, live change capture, an event stream, or a catalog scan) is chosen for you and starts as soon as you deploy it. From a terminal: dapp pipeline new.

What each kind is for

batchA table, view, file or SaaS object copied once or on a schedule, in full or only what is new or changed. The usual choice, the cheapest, and it needs only read access on the source.
cdcA database's row changes within seconds, read from its change log (PostgreSQL, MySQL, MongoDB, SQL Server). Runs continuously. The database admin must switch change capture on first.
streamEvents from Kafka, written as they arrive. Runs continuously.
metadataCopies no rows: tables, columns and lineage (and with deep, profiles, PII tags and usage) appear in the DataOS catalog.

Who may do what

A pipeline runs as the person who deploys it. They need a tenant role that may create pipelines (Tenant Admin, Data Admin or Data Developer) and Can Use on the Compute, on each Depot it reads or writes, and on the Secrets behind those Depots.

This page never grants access by itself. If you may not use a Depot, deploying says which one and offers Request access; the Depot's owner (or a tenant admin) approves it here, and only then is a grant made for that one person and that one Depot.

The Depot's own database user also needs rights on the source system: read for batch, change-log rights for CDC (for PostgreSQL wal_level=logical and REPLICATION). Those are set by the system's admin, not in DataOS.
